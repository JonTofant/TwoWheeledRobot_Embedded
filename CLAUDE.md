# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository overview

This repo holds firmware and support tooling for a biped ("Diablo") jumping/walking robot, plus a
telemetry bridge and some analysis notebooks. The main body of work is the STM32 firmware:

- `STM32_Diablo_Robot_Source/` — STM32CubeIDE project (STM32F446RETX) that runs the robot's control
  loop, state machine, motor drivers, sensor fusion, and an on-device neural-network policy. **This is
  where almost all firmware work happens.**
- `STM32_Jumping_Robot_VS_Code_Project/` — a VS Code-oriented mirror/variant of the same source tree.
- `JumpingRobotTelemetryESP32/JumpingRobotTelemetryESP32.ino` — ESP32 Arduino sketch that pairs a
  Bluepad32 gamepad and bridges UDP joystick input + UART telemetry between the game controller and the
  STM32 board.
- `Diablo_robot_source-run-{1,2,3}-model-network-ApplicationTemplate-code/` — raw X-CUBE-AI
  "ApplicationTemplate" export snapshots for successive trained policy generations. These are archival
  outputs, not the integrated build — see "AI policy / neural network" below.
- `Grafi_vzmeti/`, `meritve_vzmet_zunanji_ks.txt`, `STM_STUDIO/` — spring/measurement data, a Jupyter
  notebook for plotting, and STM Studio variable-monitor logs/config. Not part of the firmware build.
- `KroznaKinematika.SLDPRT` — SolidWorks part file.

There is no test suite, linter, or package manager in this repo — it's an embedded C project built and
flashed through STM32CubeIDE.

## Build / flash

The firmware is an STM32CubeIDE (Eclipse CDT + arm-none-eabi-gcc) managed-build project rooted at
`STM32_Diablo_Robot_Source/`.

- **Normal workflow:** open `STM32_Diablo_Robot_Source/Diablo_robot_source.ioc` or the project folder in
  STM32CubeIDE, build the `Debug` (or `Release`, if configured) target, and flash via ST-Link.
- **Headless build:** the project has a generated makefile under `STM32_Diablo_Robot_Source/Debug/`
  (built by the `arm-none-eabi-gcc` toolchain, GNU Tools for STM32 13.3.rel1). It can be invoked directly
  with `make -C STM32_Diablo_Robot_Source/Debug all` if the toolchain is on `PATH`, but this directory is
  auto-generated by CubeIDE — don't hand-edit `sources.mk`, `objects.mk`, `subdir.mk`, or the `makefile`
  itself; let CubeIDE regenerate them when files are added/removed.
- Debug launch configs (`*.launch` files at the project root) are for ST-Link debugging sessions from
  within CubeIDE/Eclipse.
- `Diablo_robot_source.ioc` is the CubeMX peripheral/pinout configuration. If HAL init code needs to
  change (clocks, pin muxing, peripheral instances), prefer regenerating from the `.ioc` file in CubeMX
  rather than hand-editing the HAL init blocks in `Core/Src/*.c`/`Core/Inc/*.h`, since those are marked
  with CubeMX `USER CODE BEGIN/END` regions that survive regeneration — code placed outside those markers
  will be overwritten.

There are no automated tests. Verification is done on hardware (bench or on the robot) and via STM Studio
variable watches (`STM_STUDIO/`).

## Firmware architecture (`STM32_Diablo_Robot_Source/`)

`Core/Src/main.c` is the entry point and owns the superloop and most cross-cutting state. Peripheral
handles (CAN, I2C, SPI, TIM, UART/DMA) are HAL-generated. The custom application logic is split into
sibling modules under `Core/Src` / `Core/Inc`, all included directly from `main.c`:

- `cybergear.c/h` — driver for CubeMars/Xiaomi "CyberGear" CAN servo actuators (the 4 leg joint motors).
  Defines the `CyberGear` struct (angle/velocity/torque/PID gains/MIT-mode fields) and the motor command
  API (`Motor_SendAngle`, `Motor_SendMITCommand`, parameter read/write, fault clearing). Global instances
  are `CyberGearMotorList[MAX_MOTORS]` and the named aliases `MOTOR_CG_LF/LB/RF/RB` (left/right,
  front/back) used throughout `main.c`.
  **Angle-frame invariant:** the CAN feedback decode for `.angle` (type-2 handler in `main.c`) and the
  MIT command encode of `desired_angle` (`Motor_SendMITCommand`) must use the exact same frame — full
  span ±4π, zero at the mechanical zero set by `setMechanicalZero()` at the folded stop, **no offset
  terms**. A historical `+M_PI_2` in the decode made `cg_angle_ref`-derived MIT targets land ~90° past
  the intended pose, driving every leg into its hard stop ("lockout"). Never reintroduce an offset in
  one place without the other; anything display-only belongs in `telemetry.c`, not the decode.
  The struct-init `kp = 30.0f` / `kd = 3.0f` match the NNDrive sim's nominal CyberGear gains
  (`cg_kp_range`/`cg_kd_range` in `nn_drive_env_cfg.py`) — the policy was trained on them, don't soften
  without retraining. Note `MIT_controler_gain_schedule_Jump/Normal()` in `controler.c` only ever write
  motor index 0.
- `DDSM115.c/h` — driver for the DDSM115 hub/wheel motors used for the chassis (referenced as
  `DDSM115MotorList`, `DDSM115setCurrent`).
- `kinematics.c/h` — leg inverse kinematics for the 2-legged platform (`MAX_NUM_LEGS = 2`): 2-solution IK
  solver (`solveIKTwoSolutions_c`), continuity-preserving solution selection
  (`chooseContinuousSolution_c`), and a spring-leg-style `LegGeometry` model (effective leg length,
  angle, Jacobian) used by the leg/posture controllers.
- `controler.c/h` — the control laws: cascaded LQI-style chassis position/velocity control
  (`calculate_cascaded_motor_currents`), pitch-leveling controller, MIT-mode gain scheduling for jumping
  vs. normal locomotion (`MIT_controler_gain_schedule_Jump/Normal`), and the top-level
  `posture_controler()` called every loop while standing.
- `StateEstimator.c/h` — IMU-based state estimation (pitch/roll/gyro) feeding the controllers and
  `isFallen()`.
- `state_machine.c/h` — global operational-state flags (`isCANReady`, `isCYBERGEARReady`, `isLOCOMOTION`,
  `isSTATIC`, `isJUMP`, `isDEMO`, etc.) and the `isFallen()` predicate. These flags gate most of the
  branches in the `main.c` superloop rather than a formal FSM table.
- `JumpStrategy.c/h` / `StartupStrategy.c/h` — higher-level behaviors (`jump_strategy_control`,
  `startup_strategy_control`) triggered from gamepad button edges (`xPressed`, `startPressed`) inside the
  main loop.
- `joystick.c/h` — parses incoming UART controller packets from the ESP32 bridge
  (`process_joystick_input`), setting button/axis state consumed by the state machine and strategies.
- `telemetry.c/h` — outbound telemetry formatting/UART transmission (`NN_buffer`, DMA UART sends).
- `system_init.c/h` — non-HAL-generated startup/init helpers.

The main loop (`while(1)` in `main.c`) is flag-driven: peripheral ISRs/callbacks set `is*Ready`/`is*` bools
(`isCANReady`, `isCYBERGEARReady`, `uart3_controller_packet_ready`, `sendUart2Data`, etc.), and the loop
body checks and clears them each pass, dispatching to joystick processing, fall detection, startup/jump
strategies, and the posture controller, then sends MIT commands to all four `CyberGear` motors.

### AI policy / neural network

The robot runs a small on-device neural-network policy via ST's X-CUBE-AI (`STAI` runtime API,
`NetworkRuntime*_CM4_GCC.a` in `Middlewares/ST/AI/`). The **integrated, actually-built** model lives in
`STM32_Diablo_Robot_Source/AI/App/` (`network.c/h`, `network_data.c/h`, `network_details.h`,
`network_weights.c/h`, `app_config.h`, `app_x-cube-ai.c/h`, `user_init.c/h`) and is wired into `main.c`
via `ann_network_context`, `ann_input`/`ann_output`, and `STAI_NETWORK_*` macros (input size 18 floats,
output size 6 floats for the current NNDrive policy; the older 8-in/2-out balance policy path is kept
under `#if !NN_DRIVE_POLICY_ACTIVE` in `main.c` for rollback). `app_x-cube-ai.c/h` here has been
hand-customized for this project's boot/inference sequence — do not blindly overwrite it from a fresh
ApplicationTemplate export.

### NNDrive sim2real port (current bring-up)

`ANN_Run()` in `main.c` implements the `Template-Twowheeledrobot-NNDrive-v0` contract from the
`~/Projects/TwoWheeledRobot` Isaac Lab repo (18 obs → 6 actions; spec in that repo's
`STM32_DEPLOYMENT.md`, env in `nn_drive_env.py` / `pure_nn_components.py`). Facts that were verified
against the sim source and must not regress:

- **Action order is `[fl, fr, bl, br]`** (`NNDRIVE_ACTION_ORDER_MODE 0`): `nn_drive_env.py` feeds
  `actions[:, 0:4]` to `_cg_ids`, built as [front_left, front_right, back_left, back_right] in
  `standup_env.py`. Modes 1–3 were experiments against the old `+M_PI_2` frame bug — obsolete.
- **CG outputs are already radians**: the exported ONNX bakes in `tanh(a) * 0.45`
  (`export_pure_nn_current_onnx.py`), so `ann_out_data[0..3]` are position targets in the sim joint
  frame; the firmware only clamps to per-corner limits (fl/br [−10°, +90°], fr/bl [−90°, +10°], same
  as sim) and slews at 3 rad/s.
- **obs[14–17] are the raw tanh action** (pre-clamp, pre-slew): reconstructed as
  `ann_out_data[k] / CG_ACTION_SCALE_RAD`, matching the sim's `tanh_action` — not the slewed command.
- **Sim frame ↔ firmware frame** goes through the folded-rest reference (`cg_angle_ref`, latched at
  boot; `CG_REF_recapture=1` in STM Studio re-latches): sim = `dir*(.angle − ref) + rest`,
  command = `ref + dir*(sim − rest)`. The obs difference tolerates a constant decode bias, the
  command does **not** — see the cybergear.c angle-frame invariant above.
- **`cg_dir[]` per-corner signs are unverified** (currently all +1). All pre-2026-07-09 bench
  conclusions (all-`−1` cg_dir, action order mode 2) were artifacts of the `+M_PI_2` bug — distrust
  them. Re-derive with `CyberGear_IndexBenchTest()` (`CG_BENCH_start=1` in STM Studio, robot on a
  stand); the bench test bypasses `NNDRIVE_OUTPUT_DISABLE`.
- **`NNDRIVE_OUTPUT_DISABLE` is currently 1** in `main.c`: `ANN_Run()` and MET/LOG telemetry run every
  15 ms tick but no motor commands are sent. Set back to 0 only after the bench retest confirms
  `cg_dir`.

There is an **older, unused** network under `STM32_Diablo_Robot_Source/X-CUBE-AI/App/` (`ann*.c/h`,
`STAI`-less naming) that is not referenced from `main.c` — don't confuse it with the live policy.

Successive trained policies are tracked as numbered "runs":
- `STM32_Diablo_Robot_Source/.ai/run/run-N/` — the raw X-CUBE-AI CLI output for generation N (analyze/
  generate/validate reports, `.ai/st_ai_output/`, `.ai/st_ai_ws/`), plus (for later runs) a full
  `AI/App/` ApplicationTemplate export.
- `Diablo_robot_source-run-N-model-network-ApplicationTemplate-code/` at the repo root — a copy of the
  same ApplicationTemplate export, kept as an archival snapshot outside the STM32 project tree.
- `STM32_Diablo_Robot_Source/.ai/run-settings.json` records the CLI args used for the most recent
  generation (source `.onnx` path, target, memory-pool config) — check this to see which run is
  "current."

When switching the integrated policy to a newer run, only the network artifacts need to move from the
run's `AI/App/` (or `.ai/st_ai_output/`) into the live `STM32_Diablo_Robot_Source/AI/App/`:
`network.c/h`, `network_data.c/h`, `network_details.h`, plus the generate report/policy-info JSON for
bookkeeping. `network_weights.c/h`, `app_config.h`, `user_init.c/h`, and `app_x-cube-ai.c/h` frequently
stay identical across runs (diff before copying) — and `app_x-cube-ai.c/h` should generally **not** be
replaced wholesale since it contains the project-specific integration code, not just generated
boilerplate. Always verify `STAI_NETWORK_IN_1_SIZE` / `STAI_NETWORK_OUT_1_SIZE` in `network.h` match
between the old and new run before swapping, since `main.c`'s buffers are sized from these macros.

## Telemetry link (ESP32 ↔ STM32)

`JumpingRobotTelemetryESP32/JumpingRobotTelemetryESP32.ino` runs on an ESP32, pairs a Bluepad32 gamepad,
and forwards controller input over UART to the STM32 (`joystick.c` parses this on the STM32 side) while
relaying IMU/telemetry data back out over UDP. Packet framing constants (`TELEMETRY_SOF`,
`CTRL_TO_STM32_START_BYTE`, `MAX_PAYLOAD_SIZE`) and baud rate must stay in sync with the STM32-side UART
config (`main.c` UART setup, `PACKET_SIZE`) and `joystick.c`/`telemetry.c` parsing — change both sides
together.
